What I built: a LangGraph ReAct-style agent on a local Ollama model, with five farm-management tools (weather, crop calendar, field status, task logging, pending tasks) and SQLite-backed checkpointing so state survives process restarts instead of resetting per run.

Concepts that clicked this week:
- Modeling the agent loop as an explicit graph rather than a black-box `.run()` call: an `agent` node decides, a conditional edge inspects `last_message.tool_calls` and routes to `tools` only when one exists, and `tools` always routes back to `agent`. Making the control flow a graph instead of hidden framework logic is what made "agent loop" stop being an abstraction.
- The `Annotated[list, add_messages]` reducer: state updates in LangGraph are merged through whatever reducer the field is annotated with, not overwritten. Without it, each node's `{"messages": [...]}` return would replace the message list instead of appending to it — silently destroying multi-turn context with no error raised.
- `thread_id`-scoped checkpointing: swapping `MemorySaver` for `SqliteSaver` separates "what state looks like" from "where state lives," so persistence became a one-line storage swap rather than a rewrite.

The gotcha: lost time debugging a `NameError` against code that no longer had the bug — the file on disk was already fixed, but I was executing it through a stale interpreter process, not the saved version. The actual lesson: when behavior doesn't match the code you're reading, check what's actually running before you re-check the code.

Open question heading into Saturday: I could see the agent's final answer, but not its intermediate reasoning — which tool it picked, why, and what arguments it passed before I get the printed result. Closed this the next day by self-hosting Langfuse and wiring a `CallbackHandler` into the LangGraph invoke call, which gave full per-node trace spans (model input/output, tool name, args, and result) instead of inferring behavior from the final printout.

Next pass: hardening the gaps Step 6 left open.

**Recursion limit.** The `agent → tools → agent` cycle's exit condition is entirely up to the model — `should_continue` only stops once it sees a response with no `tool_calls`. LangGraph defaults to a recursion limit of 25 if you never set one, so I wasn't actually unprotected, but I hadn't made a decision, I'd inherited one. Set it explicitly to 10 in the invoke config and wrapped the call in `except GraphRecursionError` so a stuck loop (a 7B local model misreading a tool result and re-calling it) prints a message and lets the REPL keep going, instead of either silently burning 25 retries or crashing.

**The try/except that guarded nothing.** Two of the five tools (`get_weather_forecast`, `lookup_crop_calendar`) had a `try/except Exception` wrapped around a hardcoded string return — no I/O, no real failure mode, nothing that exception block could ever actually catch. I'd added it for consistency with the three db tools without asking what it was protecting against. The fix wasn't a better except clause, it was deleting it — narrowing to some other exception type would've just been a different way of pretending there's a real failure mode there. The three tools that do touch SQLite kept their narrowly-scoped `except SQLAlchemyError` (formerly `sqlite3.Error`), because those genuinely can fail. Lesson: a try/except should mark a real boundary where failure is possible, not get copy-pasted onto every function out of habit.

**Moving the db layer behind SQLAlchemy.** Every db-touching tool went from raw `sqlite3.connect()`/`.close()` calls to a single module-level SQLAlchemy `engine` with an explicit `QueuePool`. I was honest with myself that pooling isn't solving a real problem at this scale — it's a single-threaded CLI processing one request at a time, there's no contention to manage. The actual reason to do it: the engine's connection string is now the only place in the file that knows it's talking to SQLite. Moving to Postgres later is a one-line change to that string, not a rewrite of five tool functions. The abstraction is the point, not the pool itself.

**A real crash, and what it exposed.** Hit `ollama._types.ResponseError: model requires more system memory (4.3 GiB) than is available (4.1 GiB)` mid-session — not a code bug, a genuine resource problem. Checked actual memory instead of guessing and found ~1 GB free out of 15.7 GB, with `vmmemWSL` alone (the WSL2 VM running the self-hosted Langfuse stack — Postgres, ClickHouse, Redis, MinIO, two Langfuse services) holding 2.4+ GB continuously in the background, on top of normal browser/editor usage. Two separate things to fix: the environment problem (stop the Langfuse containers when not actively pulling a trace, instead of leaving six containers running for an app I'm using interactively maybe once an hour), and a real code gap it exposed — the invoke call only caught `GraphRecursionError`, so any other failure, including this one, took the whole REPL down. Read the actual `ollama` client source instead of guessing what to catch, found it converts `httpx` errors into two specific types — `ResponseError` (server responded with an error) and `ConnectionError` (server unreachable) — and caught exactly those two. Same principle as the `sqlite3.Error`/`SQLAlchemyError` scoping: catch what you've confirmed can happen at a real boundary, not `Exception` broadly.

Open question now: the db layer is abstracted behind SQLAlchemy but never actually tested against anything other than SQLite. The honest next step isn't writing more code against it — it's actually standing up a local Postgres instance and pointing the engine at it, to find out if "one-line swap" is true or just a theory.

Production run, two more gaps.

**The streaming path had a different exception contract.** The `except (ResponseError, ConnectionError)` block around the Ollama call looked complete — `ResponseError` for model-side errors, `ConnectionError` for "can't reach the server." Then a real connection-refused crash bypassed both. Read the ollama client source instead of guessing. `_request_raw()` (line 137–145) does catch `httpx.ConnectError` and re-raise it as Python's builtin `ConnectionError` — that's the path the non-streaming API uses, and it's what we'd been relying on. But `ChatOllama` uses the streaming path: `inner()` (line 183–189) opens `self._client.stream()` in a `with` block, and if the TCP handshake fails at the `__enter__` call, `httpx.ConnectError` is raised before the `except httpx.HTTPStatusError` handler in that function is ever reached. Two code paths in the same library, two different exception contracts, and our catch only covered one of them. Fix: add `httpx.ConnectError` to the tuple directly. The alternative would have been `except Exception` or `except httpx.RemoteProtocolError` guessing from the traceback — neither would've been right for the actual fault mode. Reading the source was the only path to getting this narrowly correct.

**Relative paths in connection strings are ambient state, not code decisions.** Running the agent from inside `langfuse-server/` (a subdirectory) silently created fresh `agrios.db` and `checkpoints.db` files in the wrong location — no error raised, no warning, just a cold-start agent with no history and an empty task table. The cause: `"sqlite:///agrios.db"` is a CWD-relative URI in SQLAlchemy (three slashes = relative path), so what looks like a file path in the code is actually resolved at runtime based on wherever the process was launched from. Anything that needs to persist across runs is an ambient property of the shell environment if you leave it relative. Fixed by anchoring both connection strings to `Path(__file__).parent` — the directory where `main.py` lives, which is invariant regardless of CWD. The rule this exposed: if a file needs to outlive a single process invocation, its path has to be an explicit invariant in the code, not inherited from the environment.

Closing the loop: an eval suite instead of eyeballing it.

**Thirty cases, four categories, one file.** Everything up to this point had been verified by typing a question and reading the answer — real bugs, but caught by hand, one at a time, with no way to know if a later change to a tool description or the model silently broke something that used to work. `test_agent.py` replaces that with 30 parametrized cases across four categories: **tool selection** (15 cases, 3 per tool — does the model call the right tool at all, or answer from nothing), **argument correctness** (8 cases — does it call the right tool *with* the right `field_id`/`crop`, not just the right tool name), **task completion** (5 cases — does a compound request like "check field-1's status and log a task to fertilize it" trigger *every* required tool, or stop after the first), and **no-tool-needed** (2 cases — does a plain "who are you?" avoid spuriously calling a tool it doesn't need). Four categories because each is a genuinely different failure mode a 7B local model can hit — wrong tool, right-tool-wrong-args, incomplete multi-step, over-eager single-step — and a single pass/fail count would blur which one broke.

**Hermetic runs, not the app's own persistence.** The live CLI reuses `SqliteSaver` and a hardcoded `thread_id="1"` on purpose — that's what makes multi-turn memory survive a restart. Reusing that same setup in tests would make case N's result depend on whatever case N−1 left in the conversation history, since `SqliteSaver` persists by `thread_id` across runs. So the test fixture compiles the graph once per session with `MemorySaver()` instead (in-process, gone when the session ends), and every call to `run_agent` mints a fresh `uuid4()` as its `thread_id` — one compiled app, thirty isolated conversations, no case able to see another's history. `run_agent` also scans *every* message in the result for `tool_calls`, not just the final one, because a task-completion case needs to see all the tools called across the loop, not just whichever one happened to run last before the model stopped.

**Gating the live-model suite behind a marker.** `pytest.ini` marks the whole module `slow` and sets `addopts = -m "not slow"`, so a plain `pytest` run — the one that'd fire on every casual check — never touches Ollama at all. The full suite only runs on `pytest -m slow`, which needs the model pulled and the server up, takes real wall-clock time, and is non-deterministic by nature (same input, no fixed seed, can pick a different-but-still-valid tool between runs). Gating it behind a marker keeps that cost opt-in instead of a tax on every `pytest` invocation, while leaving it one flag away whenever a change to a tool's docstring, the model, or the graph itself needs checking against a regression baseline instead of a guess.

The throughline from finishing Agroteca — write the eval before, or at least instead of, trusting a good-looking run — applies at this project's much smaller scale too: a test suite bolted on after the fact only proves the agent still behaves the way I remember it behaving. Parametrizing across categories the model could plausibly fail *differently* is what turns "does it still work" into something a diff can actually answer, instead of a vibe.

Open question heading forward: the suite checks *which* tools get called and with *what* arguments, but not whether the final natural-language answer is a faithful summary of the tool result — that's the same membership-vs-faithfulness gap Agroteca's eval hit with generation, just not yet built here.

Running it for real, and the difference between a flake and a finding.

**The first scored run: 27/30 (90%).** `pytest -m slow -v --tb=short test_agent.py` end to end took 24 minutes 33 seconds on CPU against `qwen2.5:7b`: all 5 task-completion cases and both no-tool-needed cases passed clean, 7/8 argument-correctness cases passed, 13/15 tool-selection cases passed. Three failures, and the instinct from finishing Agroteca held: don't report the number, inspect what's under it — each of the three turned out to be a different kind of thing.

**One was the test's fault, not the model's.** `"Harvest window for potatoes in Chile"` failed an exact-match assertion expecting `crop="potato"` — the model actually passed `crop="potatoes"`, echoing the user's own plural wording back verbatim, which is arguably *more* faithful tool-calling, not less. Fixed by loosening that one field from an exact match to the substring match already used for `description` elsewhere in the same file (`"potato"` is a substring of `"potatoes"` regardless of which one the model returns). Re-ran the single case after the fix: passed. *Same lesson as Agroteca's q18 — a red assertion can be the label's fault, and the fix is to inspect before touching either the model or the prompt.*

**One didn't reproduce.** `"Is frost a risk for field-1 in the next 7 days?"` hit `GraphRecursionError` outright in the full run — the recursion limit of 10 (set explicitly, see the hardening-pass entry above) actually got exercised by a real case, not just a hypothetical one. Re-ran it alone with logging on: two clean turns, `get_weather_forecast` called correctly, direct answer, well inside the limit. One pass after one fail — one-for-two across everything actually run — isn't enough to call this resolved *or* call it broken; CPU inference here has no fixed seed, so neither outcome proves much alone. Flagged as a watch item, not a fix, because there's nothing here confirmed broken enough to change yet.

**One held up, and it's the interesting one.** I expected `"What's the weather forecast for field-1?"` — the case whose wording is closest to the tool's own docstring (*"Returns the daily weather forecast for..."*) — to be one of the *easiest* cases in the suite. It failed in the full run: the model answered directly, no tool call. First guess was a cold-start effect, since it's the very first live model call of the whole session — a live hypothesis, not a stretch, given Agroteca's own ONNX warm-up story (>90s → 27s on the first request). Tested it the way that project would have: reran the same single case alone in a fresh process, still the first call — failed again. Ran it a third time as a pure confidence check — failed a third time. **3 for 3.** That kills the cold-start theory outright: it isn't about being first, it's about this exact phrasing. Paraphrases of the identical intent — *"Will it rain in field-2 this week?"*, *"Is frost a risk for field-1..."* — both reliably trigger the tool. The literal, closest-to-the-docstring phrasing is the one case the model treats as answerable from the words alone instead of a real lookup. *Lesson: predicted a systems-level explanation and got a more specific, more useful one by actually testing the hypothesis instead of asserting it — the same "predict, then let reality grade it" move that redirected Agroteca's embedder experiment toward the real bottleneck instead of the guessed one.*

**Reconciled count, stated precisely** (arithmetic on what's actually been measured, not a fresh full re-run): 28 of 30 cases behave correctly once the test bug is accounted for. One case (frost/recursion) is a genuine open question with too little data to call either way. One case (the weather-forecast phrasing gap) is a confirmed, reproducible tool-selection miss — small, specific, and the next real thing to fix, most likely with a sharper docstring or an explicit "always call this tool for weather questions, never answer from memory" instruction, re-verified the same way it was found: run it, don't assume the fix worked.

Moved the project out of OneDrive. Two bugs surfaced on the way back in, neither from the code.

**A copied `.venv` carries its old address with it.** The move (OneDrive → a plain local folder, to get out from under OneDrive's sync service) was done manually after an automated move hit a Windows file-lock error. `uv run pytest` broke immediately afterward with `Failed to canonicalize script path` — a fast, clean failure, not a hang, so the interpreter itself wasn't the problem. `.venv/Scripts/python.exe -m pytest` worked fine, which narrowed it to something specific to the `pytest` entry point rather than the environment as a whole. `grep -a "OneDrive" .venv/Scripts/pytest.exe` found it: the console-script launcher embeds an absolute shebang path to the venv's own `python.exe` at the location it was created — `c:\Users\...\OneDrive\...\Agrios\.venv\Scripts\python.exe` — baked in at install time, not re-derived at run time. Copying the `.venv` folder copies that stale address along with it; eight launchers had it (`pytest`, `py.test`, `dotenv`, `httpx`, `idna`, `normalizer`, `pygmentize`, `websockets`), all silently broken the moment the old copy was deleted. `uv sync` alone didn't fix it — it only reinstalls packages whose version changed against the lockfile, and pytest's version hadn't changed, so its launcher was left untouched. Deleting `.venv` outright and re-running `uv sync` regenerated every launcher against the correct path in under 5 seconds, using uv's warm package cache. The generalizable rule: a virtualenv is a build artifact anchored to an absolute path at creation time, not a portable directory — moving the project directory doesn't move the venv with it, copying does the opposite of what you want. `.venv` is already gitignored, so nothing about this was actually gitignore-relevant, just uv-specific.

**Running the live CLI end-to-end surfaced a real, separate bug: tracing is currently broken.** Two turns through the actual CLI (`uv run python main.py`) — a plain question and a tool-calling one — both answered correctly, tool call and DB read included, so the agent itself is fine. But the Langfuse exporter logged `Read timed out` on the first turn's span, then `404 Not Found` on the second's, against the locally self-hosted instance at `localhost:3000` — which does answer on that port, so it's up, just not accepting whatever the client is sending it. Export happens on a background path that doesn't block the conversation, which is exactly why this could sit unnoticed: the agent looks like it's working perfectly from the CLI, and only the exporter's stderr output says otherwise. Not yet root-caused — most likely a version drift between the `langfuse` SDK (`4.12.0`, OTLP-based) and whatever this self-hosted instance actually expects, since a 404 on export reads like a missing/changed endpoint path rather than a bad key. Logged as a known limitation rather than guessed at, the same discipline as the eval-suite failures above: don't write down a root cause you haven't actually confirmed.

**A second, smaller thing the live run made visible that the eval suite structurally can't catch:** the eval suite's own hermetic design — fresh `uuid4()` thread per case, MemorySaver instead of the CLI's persistent SqliteSaver — is exactly why it never surfaces this. The CLI's real `thread_id="1"` has been accumulating messages across every development session since the checkpointing feature was added; it's now 25+ messages deep, and every turn replays all of it through the model before generating a token. A turn that should take single-digit seconds took 30s–2min in this verification pass. Not a bug in the sense of wrong behavior — persistent memory across restarts was the deliberate point — but a live demonstration of what "no trimming or summarization" actually costs once a thread has real history behind it, rather than a two-line eval-case conversation.

A perception/motor-control bridge, and two more bugs the compiler found before anyone else did.

**What and why.** `cpp/` adds a lock-free single-producer/single-consumer ring buffer over POSIX shared memory (`shm_open`/`mmap`), meant to carry 6-DoF pose data between a Python perception process and a C++ motor-control process with no lock and no kernel round-trip on the hot path. It's the first piece of this project meant to eventually run on real hardware (a Raspberry Pi or Jetson) rather than a laptop — nothing before it touched a real-time control loop at all. Full design writeup and the memory-ordering contract are in `cpp/README.md`; this entry is about what broke while proving it actually works.

**The compiler caught a real bug in the layout-verification code itself.** `spsc_ring_buffer.hpp` asserts at compile time that `head_`, `tail_`, and the payload buffer land at the exact byte offsets `bridge_c_api.cpp`'s C ABI (and therefore the Python side) depends on — `static_assert(offsetof(SPSCRingBuffer, head_) == 0)`, written directly in the class body. First build: `invalid use of incomplete type`. `offsetof` needs a complete type, and a class template isn't complete yet at the point in its own body where that static_assert was written — the closing `};` hasn't been reached. Fix: move the `offsetof` calls into small `static constexpr` member functions (function *bodies* are a "complete-class context" even when written inline, so `offsetof` works there), then call those functions from `static_assert`s placed after the class closes. A layout check that doesn't compile is a layout check that was never actually run — this one failed loudly instead of silently, which is the entire point of writing it.

**`ctest` reported the concurrency test passing for the wrong reason.** The correctness test (a real producer thread and a real consumer thread racing for 5,000,000 items through a deliberately small 256-slot buffer, checked for lost/duplicated/reordered items) was built on `assert()`. `cmake --build` uses `RelWithDebInfo` by default, which — like every CMake Release-family build type — defines `NDEBUG`, and `NDEBUG` compiles every `assert()` in the program down to nothing. `ctest` reported "1/1 tests passed." It was telling the truth about a test that was checking zero of its conditions. The tell was in the build log, not the test output: a warning about an unused variable (`out`) that was only ever referenced inside `assert()` calls — once those calls compile away, so does the only place that variable is read. Fixed by replacing every `assert()` with a small `CHECK()` macro that has no `NDEBUG` guard at all. Verified the fix two ways: rebuilt with `-DNDEBUG` explicitly and confirmed both the warning disappeared (the variable is genuinely used now) and the test still ran for real; rebuilt the actual CMake project fresh and confirmed the same. *Same family of lesson as the potato/potatoes test bug from the eval suite — a passing test result is a claim, not a fact, and this project's whole discipline has been to check the claim before writing it down. This one would have been very easy to ship: the binary built, ran, and printed "all tests passed," and every one of those things was true. It just wasn't testing anything.*

**Verified for real, not just "should work":** built and ran inside a Linux container (Docker, this being a POSIX-shared-memory project on a Windows dev machine that structurally can't run it natively — `cmake` refuses to configure on any OS but Linux/macOS, on purpose, rather than silently producing a binary that can't work). The 5M-item concurrency test passed clean under `-Wall -Wextra -Werror`. The actual bridge was proven end to end, not just each side in isolation: a real `motor_control_consumer` process created the shared-memory segment, and a real, separate `perception_producer_demo.py` process attached to it via `ctypes` and pushed 20 poses along a synthetic circular trajectory at 50 Hz — all 20 arrived at the C++ side in order, with correct values, followed by a clean shutdown on the sentinel pose. **Not verified:** ThreadSanitizer. `-fsanitize=thread` built fine but crashed on launch (`FATAL: ThreadSanitizer: unexpected memory mapping`) inside this specific Docker-Desktop-on-WSL2 setup, and neither of the two standard fixes (disabling ASLR via `setarch`, relaxing the container's seccomp profile) got past it — read as an environment limitation of this dev machine specifically, not a code issue, given the plain build's real 5M-item concurrent run already passed. Worth another attempt on a real Linux host or a different container runtime before trusting that read, though — TSan's happens-before analysis catches classes of ordering bug a single passing stress-test run can get lucky past, and "environment limitation" should stay a hypothesis until it's tested somewhere the environment isn't in the way.

A real-time control loop, and where "verified" has to stop.

**What got built.** `motor_control_rt_loop.cpp` + `rt_thread.hpp`: a PREEMPT_RT/ROS 2-guideline 1 kHz loop on top of the same bridge — `mlockall(MCL_CURRENT | MCL_FUTURE)` plus an explicit stack pre-fault first thing in the thread's body, `SCHED_FIFO` at priority 99, `pthread_setaffinity_np` to a chosen core, zero dynamic allocation or `std::cout` inside the hot loop (telemetry goes out through a second, in-process instance of the *same* `SPSCRingBuffer` already proven correct above, drained by a separate ordinary-priority monitor thread — reusing the primitive instead of inventing a second one), and absolute-deadline `clock_nanosleep` scheduling instead of a relative sleep so per-iteration execution time can't accumulate as drift.

**The framing question came first, and mattered.** The ask was to "refactor the 1 kHz motor control loop" — but `motor_control_consumer.cpp` was never a 1 kHz loop; it's a poll-with-sleep-and-print demo built to verify the bridge itself, and forcing PREEMPT_RT constraints onto it (no `std::cout`, no bounded exit, fixed-rate forever) would have destroyed a working, already-verified demo to satisfy a request that was really asking for something new. Wrote the real-time loop as its own file instead, reusing the bridge underneath. Worth naming this kind of thing out loud when it happens rather than silently either refusing the literal ask or silently breaking working code to honor it too literally.

**Two requirements beyond the literal four-item spec, both because "comply with PREEMPT_RT/ROS 2 guidelines" is a real, larger checklist than four bullets.** (1) `mlockall` prevents pages from being *swapped out*, but doesn't guarantee a page is *populated* before its first touch — so the stack is also explicitly pre-faulted once, before the hot loop, which requires the thread to have been created with an explicitly large-enough stack in the first place (`make_realtime_thread_attr`), not the platform default. (2) `-Wl,-z,now` on the RT executable specifically, forcing eager symbol binding — without it, the *first* call to any dynamically-linked function from inside the hot loop pays for on-demand dynamic-linker resolution, which is exactly the kind of non-deterministic first-touch latency this loop exists to eliminate, and it's an easy thing to build correctly-mechanistically and still leave a latency landmine in.

**Verified the failure path, not just the success path.** `SCHED_FIFO` and `mlockall` both need `CAP_SYS_NICE`/`CAP_IPC_LOCK` or root — privileges Docker does not grant by default even to a root user inside a container. First run, without those capabilities: `pthread_setschedparam(SCHED_FIFO, 99) failed: Operation not permitted`, reported clearly, loop refused to start, exit code 1. That's not a bug, that's the design — a control loop that silently continues at normal scheduling after asking for real-time guarantees and not getting them is worse than one that refuses to run, because it fails exactly when the load it was supposedly hardened for finally shows up. Re-ran with `--cap-add=SYS_NICE --cap-add=IPC_LOCK`: `mlockall`, `SCHED_FIFO(99)`, and affinity-to-core-0 all succeeded, and a 2,000-iteration run completed cleanly with the correct iteration count in the expected wall-clock time.

**Where the honest accounting has to stop: the jitter numbers aren't a real-time performance claim.** That same run measured a 76 μs average and 450 μs worst-case deadline miss, 76/2000 iterations over a 200 μs overrun threshold. Every layer of the actual execution environment — Docker Desktop, on WSL2, on a stock non-PREEMPT_RT-patched kernel, inside a VM, with no `isolcpus`/core isolation configured anywhere — is exactly what real-time Linux setups exist to eliminate, and none of it was eliminated here. What's actually proven: the real-time *mechanisms* work correctly once granted the right privileges, and the *timing logic* (absolute-deadline scheduling) doesn't drift. What's not proven, and shouldn't be claimed: any actual latency bound. That needs a real PREEMPT_RT-patched kernel and a genuinely isolated core to mean anything — the same discipline as the TSan gap above, a limitation named as a limitation instead of quietly reported as a number.

Closing the loop: LangGraph tools that actually talk to the RT loop, a breaking wire-format change, and a second shared-memory channel.

**Three real design questions came before any code, and guessing wrong on any of them would have meant real rework, not just style nits.** Asked instead of assuming: (1) "MCP tool schemas" turned out to mean two different things — Agrios's agent uses LangGraph's native `@tool`, not the actual Model Context Protocol, and building a real MCP server would have been a materially different, separate integration surface; went with the LangGraph-native tool, matching everything else in `main.py`. (2) The new `SubmitSpatialIntent` tool was specified to take `tvec`/`rvec` (translation + Rodrigues rotation vector — what `cv2.solvePnP`/ArUco/FoundationPose actually emit), but `Pose6D` already stored Euler angles (`pitch`/`yaw`/`roll`) — a placeholder chosen before there was a real producer to match, not a considered decision. Converting `rvec` to Euler inside the tool would have buried a lossy, gimbal-lock-prone transform behind what should be a "write bytes to shared memory" function; migrated `Pose6D` itself to `tvec`/`rvec` instead — a breaking change to a struct whose exact byte offsets are asserted at compile time and mirrored in three languages, which is exactly why it was worth confirming before touching it, not after. (3) `ReadJointStates` implied a second channel (motor control → monitoring) that didn't exist yet — needed a joint count to size the payload struct before writing a single line.

**The migration itself was mechanical once decided, and the compile-time layout contract earned its keep.** `Pose6D`'s `offsetof` static_asserts (from the earlier entry) didn't need to change — they check `SPSCRingBuffer`'s own `head_`/`tail_`/`buffer_` offsets, which don't care what's inside the payload type. Renaming `x,y,z,pitch,yaw,roll` to `tvec[3],rvec[3]` kept the same total size (56 bytes) and field count, so every place that already depended on the layout — `bridge_c_api.cpp`'s `sizeof` cross-check, the Python `ctypes.Structure` — needed a rename, not a rethink. What actually needed new thought: every place that *read* the old semantic fields (`motor_control_rt_loop.cpp`'s control-output stand-in, `motor_control_consumer.cpp`'s print statement, `perception_producer_demo.py`'s synthetic trajectory) had to be re-derived under the new representation, not just search-and-replaced — the demo's circular trajectory now uses `rvec=(0,0,angle)`, which is exactly the Rodrigues vector for a pure rotation about Z by `angle` radians, not an arbitrary substitution.

**The joint-telemetry channel is a second, independent instance of everything already built for the pose channel, not a new synchronization design.** Same `SharedRingBuffer` template, same `SPSCRingBuffer` underneath, same compiled-C-ABI-instead-of-raw-Python-ctypes reasoning, same non-owner/owner topology (the RT loop owns it, since it's the producer and the process guaranteed to be running whenever there's telemetry to report) — just a different payload (`JointState6`: 6 joint angles + timestamp) and a different shared-memory name. `JointStateBridge.read_latest()` on the Python side does something the pose side deliberately doesn't: drains the ring buffer to the newest sample instead of returning the oldest unread one. Right call for "what's the current joint state" (only the newest reading matters, older ones are backlog); would have been the wrong call for the pose channel, where every intent matters and dropping stale-but-unconsumed ones silently would be a real behavior change, not a convenience.

**Verified for real, all four pieces, not asserted from reading the code:** rebuilt the full CMake project clean after the migration; re-ran the (unaffected, still-passing) 5M-item concurrency test as a regression check; re-ran the cross-process pose demo and confirmed `tvec`/`rvec` values transfer correctly end to end; ran the RT loop and `joint_state_reader_demo.py` concurrently and got 8/8 readings with zero empty polls. Then the actual point of building this: installed `pydantic` and `langchain-core` in the container, started a real `motor_control_rt_loop` process, and from a *separate* Python process imported the real `spatial_tools` module and called the real `@tool`-decorated functions — `submit_spatial_intent.invoke(...)` reported delivery, and the RT loop's own telemetry log independently confirmed it (`pose=no` on every line until the exact iteration the push landed, `pose=yes` from there on — not just "the function returned success," a second, independent system agreeing). `read_joint_states.invoke({})` then read back a live sample from that same process. Every stage of the requested architecture exercised in one run: Pydantic validation → LangGraph tool → compiled C ABI → shared memory → real-time thread, and back.

**One genuine debugging detour, worth naming because the instinct on seeing it was wrong at first.** The first attempt at the full integration test failed: `shm_open("/agrios_pose_bridge") failed: No such file or directory`, even though `main()` creates that segment before doing anything else. First guess was a race — maybe the RT loop just hadn't started yet. Actual cause, found by checking whether the process was even alive (`kill -0 $PID`) rather than trusting the guess: it wasn't — `error while loading shared libraries: libagrios_bridge.so: cannot open shared object file`. Every earlier verification pass had mounted just `cpp/` at `/workspace` and built+run from there, so CMake's default build-tree RPATH (pointing at the absolute path `/workspace/build`) resolved correctly. This pass mounted the *whole repo* at `/agrios` instead, to reach `spatial_tools.py` at the repo root — same binary, same host files, different container path, so the baked-in RPATH pointed at a directory that no longer existed inside this container. Fixed with an explicit `LD_LIBRARY_PATH`, not a code change — a reminder that "verified in a container" is scoped to the exact mount/path setup it was verified under, and changing that setup for a *different, unrelated* reason (needing the repo root visible) can silently invalidate an assumption (the RPATH) that had nothing to do with the change being made.

A signal-handling audit, and a bug it found that every prior verification pass had masked without anyone noticing.

**The atomics and cache-line alignment held up under scrutiny; the teardown sequence didn't.** Asked to specifically audit for memory-ordering violations, false sharing, and shared-memory leaks on process termination. The first two: clean. `spsc_ring_buffer.hpp` has no `seq_cst`, no `relaxed` on a cross-thread synchronization point (the two `relaxed` loads are each a thread reading its *own* index, never written by the other side — not a synchronization point at all), and `head_`/`tail_`/`buffer_` each sit on their own `alignas(64)` boundary, confirmed by the compile-time `offsetof` checks already verified earlier this session. Nothing to fix there, and saying so plainly mattered more than padding the finding count — a real audit reports what's actually wrong, not a quota.

**The third vector had two real, confirmed bugs, both in the same place: nobody was listening for SIGTERM, and one binary wasn't listening for anything at all.** `motor_control_consumer.cpp` — owner of `/agrios_pose_bridge` — had zero signal handling: Ctrl-C or `kill` both hit the default disposition, process dies immediately, no destructors run, `shm_unlink` never executes, the segment orphans in `/dev/shm`. `motor_control_rt_loop.cpp` — owner of *two* segments — handled `SIGINT` only. `SIGTERM` is what `kill` sends by default, and what every real process supervisor (systemd, Docker, k8s) sends on shutdown before escalating to `SIGKILL` — meaning the one binary that does have graceful-shutdown code was still unprotected against the single most common real-world termination path.

**This bug was live for the entire session and never once surfaced, because every verification run this session used `docker run --rm`.** An ephemeral container's `/dev/shm` disappears when the container exits, for any reason — a graceful exit, a crash, a forcible kill, all identical from the perspective of "did the leak become visible." Dozens of test runs, zero indication anything was wrong, because the thing that would have caught it (the segment surviving past the process that owned it) was itself destroyed every time regardless of whether cleanup code ran. A real deployment — a supervisor restarting this process in place, a long-lived host instead of a disposable container — would have accumulated one orphaned segment per SIGTERM, forever, until something else happened to reopen the same name as owner.

**Fixed and verified for real, not asserted from the diff.** Both binaries now register the same handler for `SIGINT` and `SIGTERM` (a `std::atomic<bool>` flag, `store` with `memory_order_relaxed` — one of the few operations the C++ standard actually permits inside a signal handler per `[support.signal]`, with a `static_assert(is_always_lock_free)` next to it so that guarantee is checked, not assumed); `motor_control_consumer.cpp` additionally needed the flag threaded into its main loop's exit condition, since it previously had no shutdown path other than the sentinel pose or the process dying. Verified by rebuilding, starting each binary, confirming its segment(s) existed in `/dev/shm`, sending real `SIGTERM` via `kill -TERM`, confirming the process exited on its own (not force-killed) *and* `/dev/shm` was empty afterward — both binaries, both true.

**One thing the audit correctly did *not* "fix": Python never calls `shm_unlink`, and that's supposed to be true, not a gap.** The request's framing assumed the Python side should be doing owner-style cleanup on SIGINT/SIGTERM. It shouldn't, and doesn't — `spatial_tools.py` always opens both channels with `owner=False`, because the C++ side is the owner by design. A non-owner calling `shm_unlink` wouldn't be a fix, it would be a *new* bug: deleting a named segment out from under a producer that might still be running. The rest of the Python-side concern (missing `munmap`/`close` on an ungraceful kill) is a non-issue for a different reason — the kernel unconditionally reclaims every mapped page, open file descriptor, and process-local heap allocation when *any* process exits, by any means, always. Distinguishing "this looks alarming but is actually kernel-guaranteed" from "this is a real, confirmed leak" was as much the point of the audit as finding the two bugs that were real.

A second audit, four vectors this time, and two of the four "fixes" demanded would have been regressions.

**Two vectors were already correct, and saying so plainly mattered more than manufacturing a finding count.** Asked to check whether `#pragma pack(1)` was missing on the ABI structs, and whether the atomics "establish a formal memory barrier" against `-O3` reordering. Neither needed touching. `Pose6D` is six `double`s plus one `int64_t` — already zero-padding, already proven by a `sizeof == 56` static_assert that's passed roughly ten real compilations this session — and forcing byte-packing on it would have been actively harmful on the ARM64 targets this bridge exists for (unaligned 8-byte access risk), for zero benefit, since there's no padding to remove. And `std::memory_order_acquire`/`release` on `std::atomic` *is* the formal barrier being asked for — both compiler-level (the standard forbids reordering across it; `-O3` violating that would be a genuine miscompilation bug in GCC itself, not a tuning knob) and hardware-level (real `ldar`/`stlr` instructions on ARM64, which is the entire reason this bridge is built on `std::atomic` instead of hand-rolled tricks in the first place). Adding `volatile` or redundant `atomic_thread_fence` calls on top would have added nothing, and `volatile` specifically would have been a real regression disguised as caution — it provides no ordering or atomicity guarantee at all, a classic and dangerous conflation.

**A third vector didn't exist in the form asked about, and "fixing" it as directed would have made the actual problem worse.** Asked whether the hot loop uses a raw `while(head==tail)` spin, and to add `_mm_pause()` if so. It doesn't spin at all — the loop blocks on `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)` and calls `pop()` exactly once per period, confirmed by re-reading the live file before answering. A `_mm_pause()`-throttled spin still keeps the core continuously active for the whole period; `clock_nanosleep` lets the OS drop the core into a real idle state between wakeups. At 1 kHz, converting this to a spin loop *is* the thermal-budget problem the audit was worried about, not a fix for it — pause-throttled spinning earns its keep on sub-100 μs loops where OS wake latency itself blows the budget, not a 1 ms one.

**The fourth vector was real.** `mmap()` in `shared_ring_buffer.hpp` never passed `MAP_POPULATE`, and the ring buffer's payload array was never touched during construction — only `head_`/`tail_` were. One correction to the framing worth keeping precise: an untouched anonymous/tmpfs page triggers a *minor* fault (zero-page + page-table setup, no disk I/O), not a "major" one as described — but the underlying concern, an unpredictable first-touch latency spike inside the timing-critical path, was real regardless of the mislabeled severity. Fixed with `MAP_POPULATE` where available (Linux-only, guarded — no portable equivalent on macOS) plus an explicit touch pass: a write-touch (zero) for the owner, since it's about to placement-construct fresh state anyway, and a *read-only* touch for non-owners, since a physical page already being resident because the owner faulted it in does not exempt a second process from establishing its own page-table entries for it — that's a per-process cost, not a per-physical-page one, and a non-owner writing to it would corrupt live queue state.

**A fifth, unprompted improvement rode along with the ABI vector:** the existing cross-language layout check only compared `sizeof`, which can't catch two structs with matching total size but silently diverged field order — a real, if narrow, gap the audit surfaced as a side effect of re-reading the ABI code closely. Strengthened to per-field `offsetof` comparisons for both channels; the fact that the build still compiled clean afterward is itself evidence the hand-written offsets were already correct, not just newly asserted.

**Verified, including one measurement that came back showing the opposite of what a lazy read would suggest, reported honestly rather than reframed.** Built the pre-fix version from `git show HEAD~1` and the patched version side by side, ran both through `motor_control_consumer 0` (opens and constructs, but the loop body — and therefore `pop()` — never executes) under `/usr/bin/time -v`: patched showed **11 more** minor faults at construction, not fewer overall. That's not a regression, it's the fix behaving exactly as designed once the test setup is understood correctly — `--count 0` means the old code's lazy first-touch path is never exercised in *either* build, so the only way the payload region gets touched at all is the new eager pass, and +11 faults is consistent with covering the ~14 pages that region spans. What this specific comparison does *not* prove, and wasn't claimed to: a net reduction in faults incurred *during* real hot-loop operation, since neither run ever reached the hot loop. The 2 major faults that also showed up in the patched run were flagged as a likely artifact of the comparison's own construction (the old binary was hand-linked statically for the test; the new one loads the real `libagrios_bridge.so` from disk) rather than something the fix caused — a confound named, not hidden. Regression-checked separately: the real cross-process push/pop path (`motor_control_consumer` + `perception_producer_demo.py`) still transfers all 5/5 poses correctly after the change.

Real-time verification: turning "real-time safe" from a claim in comments into something the toolchain checks, and measuring latency against the standard benchmark instead of in isolation.

**The gap this closed.** Everything real-time about the control loop was argued, not checked. "No allocation, no locks, no I/O in the hot loop" lived in comments. The only latency numbers came from Docker on WSL2, and were explicitly not a real-time claim. The `MAP_POPULATE` audit's own write-up admitted its measurement never reached the hot loop. A reviewer could fairly read all of that as "trust me."

**The control step now carries a property the compiler checks.** The per-period work moved out of `rt_thread_main` into `control_tick()` (`agrios/control_tick.hpp`): one definition, shared by the RT binary and the tests. It's marked `[[clang::nonblocking]]` through an `AGRIOS_NONBLOCKING` macro, which is empty on every other compiler. Clang 20's function-effect analysis then rejects, at compile time, any call from it to something not provably nonblocking, including inside the bridge's C API (`agrios_bridge_pop`, `agrios_joint_bridge_push`), which is annotated and verified the same way. `std::sin` passes and `printf` doesn't. That was checked by planting a `printf` in `control_tick` and watching the build fail, not assumed from the docs. LLVM's RealtimeSanitizer covers the same function at run time. `rt_safety_test` drives the real `control_tick` over real shared-memory bridges with a live producer thread, exercising the no-pose, pose-received, and telemetry-ring-full paths. The real RT binary also runs 5,000 periods under RealtimeSanitizer at SCHED_FIFO. All of it runs on x86-64 and arm64, in CI.

**Both checks have negative controls, and the first draft of one shows why.** A passing check is only evidence if it would have failed. So each has a deliberate violation that CI requires to fail: a file that must not compile (`nonblocking_negative_control.cpp`), and `rt_safety_test --negative-control`, which allocates inside a nonblocking function and must be killed by RealtimeSanitizer. The first version of that runtime control didn't trip the sanitizer at all; it fell through to its own "not caught" branch. The cause: the allocation was `new int` immediately followed by `delete`, and C++ lets the compiler remove an allocation nothing observes. At `-O1`, Clang did exactly that, so there was never anything for the sanitizer to see. That's the same silent-pass failure mode the control exists to catch, caught on the control itself, and the same lesson as the `assert`/`NDEBUG` test earlier in this log. Fixed by publishing the pointer through a volatile global so the allocation escapes. RealtimeSanitizer now aborts it with a full stack trace (exit 43), and CI checks for that specific report, not just a nonzero exit.

**Measuring page faults inside the loop found one, every run.** The RT thread now records `getrusage(RUSAGE_THREAD)` immediately before and after its loop, both outside it, since `getrusage` is a system call. The answer was exactly 1 minor fault per run, every time. It wasn't the stack (pre-faulted), the rings (pre-touched), or the heap (populated by `mlockall`). It was the loop's very first `clock_gettime()`: the first time the process touched the vDSO mapping the clock is read from, which is set up lazily and which `mlockall` doesn't populate. One clock read during setup moved that fault out of the loop. It's re-measured at zero across runs, and the CI latency job now fails if it's ever nonzero. This also answers the question the `MAP_POPULATE` audit left open, whether faults during real hot-loop operation were zero, with a measurement that actually reaches the hot loop.

**Latency is now measured against cyclictest, not in isolation.** "76 µs average" means little without knowing what the platform delivers on its own. `cpp/tools/rt_validate.sh` runs `cyclictest`, the standard PREEMPT_RT latency benchmark, and the Agrios loop back to back: same core, priority, period, and `stress-ng` load. It writes a side-by-side report (`compare_latency.py`), so the absolute numbers are attributed to the platform and the gap between the columns is what the loop adds. Building it surfaced two fairness problems.
- `cyclictest` silently holds `/dev/cpu_dma_latency` at 0 to keep the CPU out of deep idle states, and the Agrios loop didn't. On any laptop that would have made the loop look worse for reasons unrelated to its code. It now holds it too, as real-time applications do (`CpuDmaLatencyGuard`), and the report records whether it did.
- The monitor thread was free to be scheduled onto the RT core. `main` now moves itself, and therefore everything it spawns, off that core before creating any thread (`keep_current_thread_off_core`).

The same script runs in CI on both architectures and on real hardware.

**The first real numbers were too good, which made them wrong.** On the first CI run, the loop's tail came out far better than `cyclictest`'s on the same runner: p99 22 µs vs 212 µs on x86-64, and a max of 241 µs vs 1,444 µs on arm64. A loop the kernel wakes through exactly the same path can't wake faster than the bare benchmark of that path, so a 10× "win" was evidence against the measurement, not for the code. Reading the script back found the bias:
- `cyclictest` always ran first, during `stress-ng`'s start-up, when it's filling 40% of RAM. The loop always ran second, after the load had settled.
- The loop's non-RT threads had just been moved off the measured core, but `cyclictest`'s main thread hadn't.

The fix makes the comparison even instead of favorable. The load warms up before anything is measured. Each tool's time is split into interleaved runs (cyclictest, loop, loop, cyclictest). `cyclictest` gets `--mainaffinity` to match. And `compare_latency.py` computes every statistic for both tools the same way, from their merged histograms (the loop's report now includes its full histogram), instead of trusting each tool's own summary. The lesson for this log: when your system beats the baseline it's built on, suspect the comparison first.

**What the development machine could and couldn't show.** This pass was built on a 2-vCPU cloud VM. The safety checks and the zero-fault result don't depend on the platform, and both were verified there. The latency numbers do: maxima swung between about 2 ms and 40 ms from run to run, for `cyclictest` and the loop alike. That's hypervisor noise, so no latency claim was drawn from that machine. That's what the CI runs and a bare-metal PREEMPT_RT run are for.
