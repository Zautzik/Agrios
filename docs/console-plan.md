# Agrios Console: plan

One local web app for everything Agrios does:
- the farm assistant, fields, tasks, weather and crop calendars, which exist today;
- the robot bridge;
- the perception cell: cameras, incidents, analytics, setup.

It runs on your own network, costs $0, and nothing leaves the site. It works in a desktop browser and on a phone in the field.

**Status: planned.** Nothing here is built yet. Licences below were checked against upstream on 2026-11-03.

## Principles

1. **The console is never in the safety path.** Alarms, relays and the fail-safe run on the perception box, the Pi and the Mega. If the console is down, the farm is still protected: the stack light still works and incidents are still recorded. The console observes, configures and reviews.
2. **One source of truth.** The console and the chat assistant call the same service functions. "Log a task" from a button and "log a task" from chat run the same code, so they can't disagree. The agent's tools in `main.py` move into a shared `agrios/services/` layer, and both front ends call it.
3. **Plain language over metrics.** Every screen says what's happening in words first ("Camera 3 lost signal 4 min ago"), with the numbers one tap away. Status is never shown by colour alone: it always has an icon and a label too, which helps colour-blind users and anyone in bright sun.
4. **Evidence stays visible.** An analytic can't be switched from shadow mode to armed (allowed to trip relays) until its measured false-alarm bound supports it, which takes at least 3 alarm-free camera-days. The UI enforces the project's "no claim without evidence" rule rather than just documenting it.
5. **Privacy by default.** The console is reachable on the local network only, and every login is required. Footage access is logged. Worker-facing analytics are anonymous per-zone aggregates unless you turn identity tracking on, after the notice question from Phase 0 (Q6) is settled. Footage expires automatically.
6. **Everything adjustable from the UI, except the safety invariants.** Thresholds, models, units, network exposure, home-screen layout, retention: every setting is editable in **Settings**. Each one is validated, shows its default, and records who changed it and when. Fixed by design and shown read-only:
   - the 250 ms fail-safe timeout, the 50 ms heartbeat, and the requirement that an alert needs at least 2 consecutive frames;
   - arming an analytic, which unlocks on evidence rather than on a toggle.

   Secrets never appear in the UI. Camera credentials go into the OS credential store (Windows Credential Manager, via `keyring`, MIT).
7. **Runs as a demo for anyone.** `agrios-console --demo` starts with a separate demo database and synthetic data: fields, tasks, and later synthetic camera streams and incidents generated by `vision.synth`. A "Demo data" banner is always visible. Someone reviewing the repo can see every screen without a farm, cameras or the Pi. The assistant still needs Ollama; without it the screen says so plainly instead of faking replies.
8. **Small and maintainable by one person at about 11 h/week.** Python end to end, no JavaScript build chain, server-rendered pages with small interactive islands.

| Screen | For | What's on it |
|---|---|---|
| **Today** (home) | "Is everything OK, and what needs me?" | A health strip mirroring the stack light (each camera, perception, Pi, Mega heartbeat), the review queue, frost/rain flags, pending tasks, the harvest window, and a box to ask the assistant |
| **Assistant** | Talking to Agrios | The existing LangGraph agent with streamed replies. Each tool call it makes is shown in plain words ("checked the forecast for field-1"), so answers can be traced. Conversation threads are the existing checkpointer threads. It can discuss an incident or a chart you're looking at. |
| **Farm** | The current Agrios features | Fields (crop, region, status, crop-calendar windows); tasks (log, complete, see pending); a 7-day weather view with frost and rain days marked |
| **Incidents** | Reviewing what perception flagged | A queue of cards, each with a keyframe strip, the vision model's summary, type, camera, time and the track involved. Buttons **Confirm / Reject / Not sure**, with keyboard shortcuts for fast triage. Filters and export. **Your verdicts become the calibration data** that bounds false alarms. |
| **Cameras** | Camera health and live view | A snapshot grid, with live video on demand. Per-camera frame rate, dropped frames, tamper and quality flags (blur, glare, covered lens, IR switch), and mode (shadow or armed). |
| **Analytics** | Trends over time | **Gait:** each animal's asymmetry trend, with "flagged since". **Aggression:** time-of-day heat strip and pair counts. **Security:** geofence entries and dwell times. **Workshop:** station occupancy and cycle time vs takt, anonymous by default. **Reliability:** false alarms per camera-day with the 95% bound, per camera and per analytic. |
| **Setup** (⚙) | One-time configuration | The camera wizard (below), users and roles, footage retention, privacy mode, notifications, language |
| **Hardware** (⚙) | The robot bridge and safety chain | Pi and Mega status, heartbeat age, the last real-time latency report, joint telemetry (today's `read_joint_states`), and a relay test that needs a confirmation step and is logged |

### The camera setup wizard

```
 1 Connect     2 Check view    3 Calibrate ground    4 Draw zones    5 Shadow mode
 RTSP URL  →   live snapshot → click ≥4 floor points → polygons     → runs, logs only
 [Test]        tamper check    type their metres     (geofence,     → "Arm" unlocks once
                               see the reprojection  storage,          ≥3 alarm-free days
                               error in cm           workstation)      are recorded
```

The calibration step shows its own accuracy: after you click the points, it projects them back and reports the error in centimetres. You know whether "the cow is 2 m from the fence" can be trusted before anything depends on it.

## How it fits together

```
 Browser (desktop / phone)
    │  HTTPS, local network only
    ▼
 Agrios Console (FastAPI, on the Windows box)
    ├── agrios/services/ ─── the same functions the chat agent's tools call
    │     ├── farm: fields, tasks, weather, crop calendar ── SQLAlchemy DB (SQLite / Postgres)
    │     ├── assistant: LangGraph agent (Ollama), streamed ── checkpointer
    │     ├── incidents & analytics ── incident DB + keyframes in data/ (gitignored)
    │     └── health ── perception workers, Pi status over the network
    ├── live updates: Server-Sent Events (status changes, new incidents)
    └── live video: MediaMTX turns RTSP into WebRTC for the browser (on demand)
```

- **Server-rendered pages with htmx**, plus Alpine.js for small interactive pieces (the calibration canvas, polygon drawing). There's no Node toolchain; pages are Jinja templates. One language (Python), one process, easy for one person to maintain.
- **Styling:** hand-written CSS with design tokens (custom properties for colour, spacing and type), light and dark themes, no build step. Tailwind's standalone CLI stays an option if the CSS outgrows this.
- **Charts:** uPlot, which is small and fast for long time series.
- **Floor plans and zones:** Leaflet with a simple flat coordinate system, so the ground-plane map, zones and tracks draw over your own site plan image. **No online map tiles**: farm coordinates are sensitive and stay off third-party servers.
- **Real-time:** Server-Sent Events, one-way from server to browser. That's simpler than WebSockets and enough for status and new incidents.
- **Auth:** local accounts with argon2 password hashing and three roles:
  - **Owner:** everything.
  - **Operator:** review incidents, manage tasks.
  - **Viewer:** read only.

  Sessions use secure cookies, and HTTPS uses a local certificate (mkcert).
- **Away from the farm (optional):** a self-hosted WireGuard VPN with Headscale. That's $0 and the control plane is yours, so you can reach the console from your phone without exposing it to the internet.
- **Language:** English first. Every string goes through gettext (Babel) from day one, so Spanish can be added later as a translation file rather than a rewrite.
- **Network exposure is a setting:** this machine only (default), the local network, or specific address ranges. Changing it is flagged "restart required". Off-site access through a self-hosted VPN (Headscale and WireGuard) is documented with a status check in **Settings**; installing the VPN itself happens outside the browser.

### Alternatives considered

- **Streamlit or Gradio:** fast to prototype, but weak on multi-user auth, custom canvases (calibration) and a polished mobile experience.
- **React SPA:** the richest option, but it adds a second language, a build chain and twice the code to maintain at 11 h/week.

htmx reaches about 90% of the polish at a fraction of the upkeep.

## How it's verified

Same rules as the rest of the repo: evidence and negative controls.
- **End-to-end tests** (Playwright) run in CI on synthetic data only:
  - every screen loads;
  - the main workflows complete: log a task, review an incident, run the camera wizard against a synthetic RTSP stream.
  - Negative control: a deliberately broken workflow must fail its test.
- **Access control tests:** every page and API route is requested as each role and as a logged-out user. The test asserts the exact allowed set, so a new route that forgets its permission check fails CI.
- **Accessibility:** automated checks for contrast, labels and keyboard navigation (Lighthouse or axe, see licences), and status is never conveyed by colour alone.
- **Measured usability, not claimed:**
  - a short task-based test with 3–5 real users (you and the people who'll use it);
  - tasks timed, e.g. "find last night's incidents and confirm one";
  - success rate and time-on-task recorded;
  - System Usability Scale (SUS) scores.

  "Intuitive" goes in the README only with those numbers beside it.
- **Performance:** page load and new-incident latency (incident recorded to card on screen) as p50/p95, measured on the Windows box and on a phone over Wi-Fi.

## Delivery

The console is built in four milestones that run alongside the vision phases. Each one is usable on its own.

| Milestone | Scope | Depends on | Estimate at ~11 h/week |
|---|---|---|---|
| **C1: Console and farm** | Shared `agrios/services/` layer (refactor of today's tools); auth and roles; **Today**, **Assistant**, **Farm**; Spanish/English; Playwright CI | Nothing in vision; can start now | 3–4 weeks |
| **C2: Cameras and setup** | **Cameras** screen with health and live view (MediaMTX); the **setup wizard** with calibration and zones | Vision Phases 2–3 (ingest, ground-plane mapping) | 3 weeks |
| **C3: Incidents and analytics** | **Incidents** review queue feeding calibration; **Analytics**; **Hardware**; notifications | Vision Phases 5–6 | 4 weeks |
| **C4: Arming and polish** | Shadow-to-armed workflow gated on evidence; retention and privacy settings; usability test with SUS; docs | Vision Phase 7 | 2 weeks |

With C1–C4 the total project grows by about 12–13 weeks of your time.

**Recommended order:** start C1 right after vision Phase 1 merges, before vision Phase 2. It gives you a usable product immediately for the farm features you already have. It also builds the service layer and app shell that every vision screen later plugs into. Its auth and roles have to exist before any camera footage is shown in a browser anyway.

## Decisions (2026-11-03)

- **Configurability:** everything adjustable from the UI, with the safety invariants above fixed. Remote access is a setting too: local only by default, with the VPN optional.
- **axe-core:** allowed as a CI-only accessibility check.
- **Users:** one owner, you. The role model is still in the code, so adding users later is a setting, not a rewrite.
- **Audience:** the repo is also a portfolio for prospective employers. Hence the demo mode, screenshots captured by CI and Architecture Decision Records (`docs/adr/`). Every README claim keeps its measured numbers beside it.
- **Language:** English first, gettext-ready.
- **Order:** C1 next, before vision Phase 2.
